2. WHAT WAS COMPLETED
=====================
The original merge had 20 conflicted files / 39 hunks. On resumption, four
files / 20 hunks remained. These were resolved semantically, preserving the
proven JSRF fixes while adopting upstream architecture. Already staged files
were revisited only when tests, builds, or runtime evidence exposed a defect.
No reset, clean, stash, rebase, merge abort, or wholesale ours/theirs replacement
was used. Preserve local work and evidence if continuing.

Important resolutions and regression traps:

* Function boundaries: retained padded INT3 termination within upstream's
  return/jump, forward-target, and embedded-switch logic. INT3 followed by at
  least two NOPs can terminate; an unpadded debug trap does not. Reachable
  forward targets must still be included.

* Atomics: retained XADD/LOCK XADD and CMPXCHG widths, memory updates, returned
  old values, and flags. Existing 15 tests cover these, including compiled
  atomic helpers and ADD flags. AddRef/Release depends on these semantics.

* MMX / bit scans: adopted upstream RecompMmx unions/helpers and upstream
  inline bit-scan logic. Removed obsolete duplicate local implementations.
  Tests retain width, zero-input, and flag requirements using upstream's
  operand snapshots. Do not reintroduce the old uint64 MMX register model.

* FS / TLS: preserved per-thread g_fs_base accessors. The renamed mem_seg field
  must add FS base exactly once; upstream formatting plus local FS_MEM had
  added it twice. Primary TIB is relocated to 0x1000; worker TIB/TLS support and
  upstream XBE TLS initialization remain. Fake PRCB is at 0x761000. RtlUnwind
  uses the current thread's FS base, not a hard-coded primary TIB.

* AV: retained upstream unshifted AV standard IDs and AV_STANDARD_SHIFT, with
  the correct guest option numbers. Numeric option 6 must return 0x00480104,
  including the dashboard 480p flag. The regression asserts this literal ABI
  value so constants and implementation cannot drift together unnoticed.

* Kernel: preserved 32-bit guest layouts, guest-token validation, device
  extension lifetime, completion/APC marshalling, thread handling, AC97
  readiness, vblank acknowledgement, AArch64 MMIO traps, and macOS mappings.
  Partition0 remains the 512 KiB configuration device; Partition5 remains the
  sparse 750 MiB device. Upstream additions were integrated and duplicate
  wrappers, cases, and globals removed.

* Partition1: maps to writable save storage via to_save1. Mapping it to the
  game directory via to_save0 caused an early firmware exit. Do not restore
  that mapping blindly; TDATA/UDATA must be writable.

* Discovery: tools/func_id/output.py excludes tail_jump_alias entries from
  authoritative function bodies used to reject independent vtable seeds.
  Canonical function bodies still protect true interior instruction entries.
  Added the exact JSRF SEH prologue 6aff68<imm32>64a100000000 to the existing
  prologue guard, recovering the proven seed at 0x0007BE30.

* Immediate-reference admission: 0x001600CA is the second byte of TEST ECX,ECX
  at 0x001600C9, not a standalone LEAVE function. Upstream discovery admitted
  it, truncated QueryInterface at 0x00160080, and corrupted the stack before
  Release at 0x001664D0. Applied the existing instruction-covering/prologue
  guard to _pass_imm_ref_targets. Focused tests are in
  tools/disasm/test_imm_ref_targets.py and tools/func_id/test_seed_output.py.

* POSIX contiguous allocation: retain the current guest-heap fallback in
  xbox_ContiguousAlloc(size, alignment), with at least 4096-byte alignment.
  Upstream's separate high-address arena gave the framebuffer 0x80084000;
  the POSIX GPU executor cleared low physical offset 0x84000 in guest RAM,
  overwriting code. The raster self-test reproduced a guest fault with
  magenta F81F values in registers. Windows keeps upstream's arena, and
  fixed-address pinned buffers retain their separate window. Full physical
  address translation remains out of scope; do not simply remove the fallback
  or OR all GPU addresses into the high window.

* Build integration: src/kernel/recomp_debug.c separates debug-service output
  from overridable tracing in recomp_trace.c. Windows FMV access is guarded.
  Missing portable declarations/includes were supplied. The local framebuffer
  stub is non-Windows only, so it cannot mask upstream's Windows presenter.
  regenerate.sh copies the canonical templates/runtime/recomp_types.h into
  generated output, where it is included first.

6.1 THE STARTUP-COUNTER GAP IS CLOSED, NOT JUST EXPLAINED
Section 4 records it as UNASSIGNED. It was the disk cache. Upstream's
Partition3/4/5 rules gave \Device\Harddisk0\Partition5 a mapping it did not
have before; the cache probe used to fall through to "Unrecognized Xbox path"
and fail, and JSRF read that as "no cache" and loaded from the disc. With the
rule the probe succeeds, so the title starts caching, and every cache write
then failed: it writes through Z:\Media\Font\jetfont.dat~ without creating the
directories above it, and Font is not among the directories it makes at
startup. The lower counters were the title getting FURTHER into a path that
could not be served, giving up, and loading less. Not a translation or
renderer regression.

Fixed in kernel_file.c by creating parent directories whenever the disposition
creates, keyed on O_CREAT so it cannot drift from posix_open_flags.

6.4 WHY THE RENDERER IS NEVER ASKED TO DRAW
Section 5 points at ROUTE_B_PLAN sections 15/16 and frames the remaining work
as a game state machine to be costed separately. The answer is simpler:

    JSRF IS SITTING IN ITS DISC-ERROR DIALOG.

The object that writes JSRF_FATAL.ERR is stable across runs at 0x01943200,
vtable 0x001CC660, and its constructor copies a string into +0xA0:

    "There's a problem with the disc $nyou're using. $nIt may be dirty or
     damaged."

It never asks for a scene because it never reaches one. Section 15's
observations all fit: the renderer serves resource and query calls because the
dialog needs them, and slot 10 and the state setters are never reached because
there is no scene. The decision to write the marker is one instruction, at
0x0006EE5C:  test [esi+0x98], 0x400000 / je / call sub_00012770.

The dialog is built by sub_0006F450, message id 0x12B0, flags 0x10003 (both
visible in the instance at +0x08 and +0x04). FOURTEEN sites call it. Which one
fires is the open question, and it is now the highest-value one in the tree.

7. THE DISC ERROR WAS OURS — rdtsc  (commit 296a0a2)
================================================================================
Supersedes 6.4's "which of the fourteen callers" as the open question, and
supersedes ROUTE_B_PLAN section 15's conclusion.

THE CHAIN, end to end:
  sub_00145560 is JSRF's QueryPerformanceCounter and is literally `rdtsc`.
  sub_00145571 is its QueryPerformanceFrequency and returns the constant
  0x2BB5C755 = 733333333, the Xbox CPU clock. The title times a startup step
  and at 0x00025370 compares elapsed ticks against 0xE4E1C0 = 15000000, about
  20.5 ms. Over that it tail-jumps (0x0002537E) to sub_0006F730, which does
  `push 0x400000` at 0x0006F732 -- the exact bit tested at 0x0006EE5C -- and
  raises the disc-error dialog. The tail jump is why the guest backtrace showed
  the tree-walker's return address: dispatch is legitimate, vtable 0x001CB0A8
  slot 1 really is sub_00066440.

  rdtsc lifted to "/* TODO: rdtsc */". THAT IS NOT A NO-OP. EAX and EDX keep
  what they held, so the title sampled two stale registers, subtracted them,
  and compared garbage against its threshold. It failed every run, on this tree
  AND on the pre-merge one.

FIXED in src/kernel/recomp_tsc.c (monotonic host clock scaled to 733333333),
declared in templates/runtime/recomp_types.h, emitted by tools/recomp/lifter.py.

7.4 METHOD WORTH REUSING
Hand-editing build-macos/.../gen and rebuilding is a cheap, non-destructive way

not touch the seed accumulator, and a regeneration discards it. That is how the
disc-error call site was identified (a probe at sub_0006F450 and sub_0006F730
printing MEM32(esp), since each call site pushes a distinct return address) and
how the rdtsc fix was validated before touching the lifter. Note the guest
tracing hooks in guest_trace.h CANNOT do this -- see 6.6.

14. THE INPUT PATH, FOLLOWED TO THE HARDWARE  (commit 1698432)
================================================================================
Following 13.5 item 1. The title's input path is the XPP section, and XPP is a
USB stack: it drives the OHCI host controller at 0xFED00000 directly rather
than going through any driver this runtime provides. That is why nothing in
src/input is reachable (13.2) -- the guest was never going to call it.

14.1 TWO REGISTERS THAT PLAIN RAM GOT WRONG  (measured, RECOMP_OHCI_DUMP=1)
Before:
    +0x08 HcCommandStatus = 0x00000001   HostControllerReset STILL SET
    +0x48 HcRhDescriptorA = 0x00001200   NDP = 0 -- ZERO DOWNSTREAM PORTS
    +0x54 HcRhPortStatus  = 0x00000000
    +0x18 HcHCCA          = 0x01452000   the stack really did initialise
HCR is self-clearing on hardware; on RAM the reset never finishes. NDP is
read-only and reports the port count; XPP writes the register for NPS/NOCP and
on RAM that write zeroes NDP too. A root hub with no ports can never have
anything attached.

Both are now held from the NV2A ack tick (xbox_McpxHoldRegisters), which is
where the existing note in that file said such things belong. After:
    +0x08 = 0x00000000    +0x48 = 0x00001202 (NDP=2)    +0x54 = 0x00000000
Two ports is a CHOICE, not a measurement. RECOMP_OHCI_PORTS overrides it.

14.2 THIS DOES NOT ATTACH A CONTROLLER
Port status stays zero, which is an honest "nothing plugged in" instead of the
previous "no ports exist". Game behaviour is UNCHANGED: 12 opens, three cached
files, no JSRF_FATAL.ERR. Do not record this as having unblocked anything.
Giving JSRF a pad means descriptors and control transfers through the HCCA at
0x01452000 -- real device emulation, sized as its own piece of work.

14.3 CORRECTION MADE DURING THIS INVESTIGATION
I inferred mid-way that the ~100k KeRaiseIrqlToDpcLevel/KfLowerIrql pairs per
20s were USB polling. They are not. sub_001BD5FF is a generic interlocked
read-and-reset helper called from all over the game code, and the OHCI init
sub_001BD14A runs EXACTLY ONCE -- probed and counted in the generated code. The
USB stack is not spinning; it initialised and went quiet.
