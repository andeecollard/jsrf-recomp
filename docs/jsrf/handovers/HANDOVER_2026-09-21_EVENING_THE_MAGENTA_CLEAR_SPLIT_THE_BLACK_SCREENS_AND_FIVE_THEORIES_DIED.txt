====================================================================
1. THE INSTRUMENT THAT SPLIT THEM: RECOMP_CLEAR_COLOR_FORCE
====================================================================

THE PROBLEM IT SOLVES. gpu_nonzero counts NONZERO pixels. So

    "nothing covered these pixels"        and
    "something covered them and wrote 0"

are THE SAME READING, and they need OPPOSITE fixes. Every instrument this
project has had reads a black screen identically whichever it is.

RECOMP_CLEAR_COLOR_FORCE=<hex> clears to that colour instead. 0xF81F is R5G6B5
magenta and nothing in this title is magenta, so anything magenta on screen is
bare cleared surface no draw ever touched. s_gpu.clear_color is left alone, so
[CLEAR-WIN] keeps reporting what the GUEST asked for rather than the override
-- an instrument that reported our own override back would be measuring itself.

THE RESULT, and it is the finding of the day:

    NOW LOADING       TOTALLY MAGENTA        nothing covers it
                                             -> a COVERAGE fault
    LOAD SCREEN       MAGENTA FADING IN
                      AND OUT                covered, driven to zero
                                             -> a SHADING fault
    INTRO SILHOUETTES 56,997 pixels ZERO     covered, written as zero
                      on a magenta surface   -> a SHADING fault

Only a draw writing zero can turn a magenta pixel black. THE TWO BLACK SCREENS
ARE NOT ONE BUG AND NEVER WERE, and now that is measured rather than argued.

Both readings came from the player's eyes. The 56,997 figure is from [FB]
nonzero=96603/153600 at t=12-16 of last-run_2026-09-21_1453_MAGENTA-CLEAR.

THREE MAGENTA RUNS MEASURED NOTHING because they never left the attract loop
([APU-VOICE] on=5, and the 4-12 band is the attract loop). CHECK on= BEFORE
READING A RUN. The Load-screen numbers below come from the fourth.

====================================================================

REPRODUCER: boot -> START -> main menu -> Load. ~40 s. Signature is 28 draws
per frame in [STAGE], which is how you know you are on it.

MEASURED, last-run_2026-09-21_1400_LOADMENU-CENSUS:
  positive control PICTURE-HELD t=17.86-46.09 on the visible main menu,
  then GPU-BLACK from t=46.09 to the end, 142 of 155 reports, four surfaces
  held, every one zero on the GPU AND in guest RAM.

MEASURED, last-run_2026-09-21_1505_COMBINER-LOADSCREEN:
  viewport scale=(320.0 -240.0 16777215.0 0.0), clip 640x480+0+0  -- textbook
  [CLEAR-WIN] the guest asks for 0x00000000 and nothing else, ~1200 times a
    window. THE CLEAR IS NOT THE BUG. It clears to black because games do.
  blend states in use include src=0x306 dst=0x0 -- GL_DST_COLOR, GL_ZERO, a
    MULTIPLY. That is what the player sees eating the magenta.

THE AFTERNOON HANDOVER DISMISSED THAT BLEND and I repeated the dismissal. The
reasoning was "it appears at the same boot position in the Roboy run, which
then rendered for another 1,050 s, so it is not a discriminator". That is
wrong. A fade-to-black multiply is NORMAL -- every game has one. Multiply by
white is a no-op; multiply by zero is permanent black. The existence of the
blend was never the question. THE SOURCE COLOUR IS.


====================================================================
3. THE COMBINER IS INNOCENT, AND THAT IS THE USEFUL PART
====================================================================

RECOMP_COMBINER_TRACE=1 with RECOMP_PB_EXEC_TOP=400, on the Load screen. First
time either has been armed in a preserved run. 15 distinct configs, all
`result=prepared`, all `rejected=0 inline=0 invalid-position=0
collapsed-xy=0`. Config 14, running on that screen:

    COLOR_ICW  08040000   TEXTURE0 x PRIMARY_COLOR  -> SPARE0
               090C0000   TEXTURE1 x SPARE0         -> SPARE0
               0C200000   SPARE0 x 1                -> SPARE0  (pass-through)
    COLOR_OCW  00000C00   AB discard, CD discard, sum -> SPARE0
    FACTOR0/1  FFFFFFFF   white

An ordinary modulate chain, and the output control word WRITES THE SUM. So the
CD/AB-nibble class of fault -- a missing write rather than a wrong colour --
is NOT what is happening here.

WHICH LEAVES THE INPUTS. Anything times zero is zero, so if SPARE0 comes out
black then TEXTURE0 or PRIMARY_COLOR is black going in. That is now the whole
question for this screen.

TWO PIECES OF INDEPENDENT SUPPORT FOR THE TEXTURE SIDE:
  - The map screen renders as FLAT UNTEXTURED SILHOUETTES with the place names
    legible on top (glyphdump report104.bmp, and the player's 14:34 capture).
    That is what a texture sampling to a flat colour looks like.
  - The afternoon handover records ZERO texture uploads in the whole black
    period, 802 before and 802 after, EVERY REQUEST A CACHE HIT. A cache hit
    that returns an empty texture is indistinguishable, in that counter, from
    a correct one. The counter was read as exonerating; it is not.

THE NEXT RUN, and it is narrow: RECOMP_FF_BATCH_WATCH_TEX and
RECOMP_FF_BATCH_DUMP_TEX exist and NEITHER HAS EVER BEEN ARMED. They dump what
a batch's texture actually holds. If TEXTURE0 on those draws is empty or
wrong, that names the bug -- and unlike everything chased today it would
explain the flat map, the black Load screen and the black silhouettes
together.

cutscene" on 21 Sep. And every in-session level load in every log that reaches
one reads LIT in the load second (ROBOY t=251/459/547/1034; the 14:18
playthrough t=280/487/538; the 10:15 run t=211).

TWO READINGS AND THEY ARE NOT SETTLED:
  (a) it renders and we lose it -- a coverage fault, as above;
  (b) it renders and FLASHES PAST. Our loads finish in ~2 s off an SSD where
      the Xbox took 8-15 s off DVD, and the title shows the screen for exactly
      as long as the load takes. The player remembers a turquoise Now Loading

NO LOADING-SCREEN FRAME EXISTS IN ANY CAPTURE. The windows are ~2 s and the

The loading screen has a name and its asset is fine: CProgress::Show
0x000666F0, DrawListDefault 0x00066550, and Media/Progress/Progress.dat,

8. THE TEXT DEFECT HAS A SECOND MODE, AND IT IS TODAY'S MODE
====================================================================

MEASURED FROM PIXELS by an agent, in scenes nobody had scored:

  MODE A, head replacement. Confirmed independently: `w` -> `"` and `y` -> `$`,
    which is exactly page-1 cell indices drawn against page 0, with BOTH
    glyphs still present underneath (more ink in the corrupt frame, not less).
  MODE B, NEW AND NEVER WRITTEN DOWN. The page-1 batch draws NOTHING -- no
    substitution, no extra ink -- and the count of missing characters equals
    the count of 0x76-0x7F characters in the line, exactly, across four
    distinct strings. Mode A appears in ZERO of today's nine bubble frames.
  A THIRD STATE: only the CJK-page batch survives; both Latin batches and the
    name label vanish.

RULED OUT: atlas corruption and wrong texture format -- the same glyph renders
right and wrong in ONE frame. Re-layout, truncation and typewriter artefact --
the surviving glyph sits at the identical x.

THE INVERSE-LENGTH RULE SHOULD BE DROPPED AS EVIDENCE. Every mode-A victim in
the corpus is the same 3-quad NAME-LABEL batch, so "short" is confounded with
"which batch"; and mode B's damage tracks the page-1 character count, which
grows WITH length. The save-screen ordering satisfies both modes and
discriminates nothing. Treat "which batch, and what happened to it" as the
variable.

CORPUS HYGIENE: glyphdump-2026-09-21-SAVEPOINT-KEEP is FOUR RUNS IN ONE
DIRECTORY -- report indices are reused, so a short run leaves an older run's
higher-numbered frames in place. 348 of its 607 frames are from 19 September
and it contains no save screen.
