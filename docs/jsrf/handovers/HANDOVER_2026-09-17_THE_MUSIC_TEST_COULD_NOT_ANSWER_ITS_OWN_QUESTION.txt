1. THE CORRECTION THAT MATTERS MOST: on_2d CANNOT ANSWER THE MUSIC QUESTION
=============================================================================

The previous handover armed [APU-POOL] on_2d to settle whether the music dying
was our defect, and stated the rule as:

    on_2d climbing while 2D heard is frozen = OUR defect
    Both frozen = the game played no music and there is nothing to fix

The player played. BOTH ARE FROZEN -- on_2d=10, 2D heard=297236 -- AND THE
GAME PLAYED MUSIC. They heard it start and heard it break up. 2D heard climbed
steadily to 297,236 before it stopped.

THE FLAW: on_2d counts the guest STARTING a 2D voice. A streaming music track
starts one voice and then feeds it; it never starts another. So on_2d flatlines
during perfectly healthy playback, during silence, and during a stream that
died mid-flight. It cannot separate the three, which is the only thing it was
added to do. It is the tenth instrument this tree has retired for that.

WHAT ACTUALLY SEPARATES THEM, and it was already in the log:

    guest_methods   frozen  ->  the guest has stopped driving the APU
    idle_trap       climbing ->  we are still telling it to

4,757 raises with not one guest response, in the window I first looked at;
41,667 raises against a frozen guest_methods over the session. That pair is
the instrument. on_2d should be deleted or re-worded before it misleads again.

WHAT IS STILL TRUE AND UNEXPLAINED: the front end is trapped on 293,206 of
968,096 frames in 38,929 short episodes (mean 7.5 frames, longest 23). So

the thread to pull.

DIRECTSOUND IS NOT OURS TO REFACTOR. src/audio/dsound_device.c is a 386-line
stub whose own header says it "accept[s] all method calls silently" with real
playback "deferred to a later phase". The DirectSound that matters is the
title's own XDK code, statically linked into the XBE and recompiled -- the ISR
at guest addresses 001A24BE and 001A25AA that apu_vp.c's comments describe. We
cannot restructure it. The only levers are what the APU model and the kernel
present to it. So the question is not "refactor DirectSound", it is "which
guest thread issues APU methods, and what is it blocked on after report 26".

4. G3 IS MEASURED, AND THE ANSWER IS GO
=============================================================================

The previous handover ranked "a per-frame sync HISTOGRAM" first because the
cumulative 7.9 ms/frame could not say whether the stall sits on the MEDIAN
frame or only on the tail. It is built and it has run. 240 s scripted
gameplay, RECOMP_METAL_FF=1:

  [FRAME]  flips=9480  mean=16.79 ms (59.6 fps) p50=18.5 p90=24.5 p99=40.0
  [SYNC]   frames=9479 mean=8.36 ms  p50=9.0  p90=13.0 p95=14.0 p99=16.0
  [NOSYNC] frames=9479 mean=8.43 ms  p50=8.0  p90=13.0 p95=14.0 p99=29.5
  [SYNC] budget 16.68 ms: reachable without the sync stall
         (NOSYNC p50=8.0 ms), clamped frames=0

NOSYNC is frame time minus THAT FRAME'S sync -- what the frame would have cost
had sync been free. Its p50 is 8.0 ms against a 16.68 ms budget, so removing
the surface-swap stall DOES move the median inside budget. G3's step 2 is
justified. clamped frames=0 is the positive control: the subtraction was
legitimate on every frame.

AND A NEW FINDING THE CUMULATIVE SPLIT COULD NOT GIVE: sync owns the MEDIAN
but NOT the tail. [SYNC] p99 is only 16.0 ms while [NOSYNC] p99 is 29.5 ms and
its max is 211 ms. This work buys 60 fps. IT WILL NOT FIX THE HITCHES. Do not
promise that it will; the tail is a different owner and a separate hunt.

It also reproduced the previous handover's census exactly: 18,942 surface
swaps against 9,504 flip syncs, 18,937 of 18,942 swaps being rebinds at a 100%
cache hit rate.

STEP 2 NEEDS A RANGE-AWARE WRITEBACK FIRST, which the previous handover did
not call out. nv2a_pb_exec.c defines

    #define nv2a_gpu_sync_range(target, bytes) nv2a_metal_sync()

-- it takes the range and throws it away. snapshot_surface() is the flip's read
of guest RAM and passes the real flipped range, but the Metal side only ever
writes back the BOUND surface, and the superseded plan already noted the live
surface is never the one being flipped. So deferring the swap's writeback
without a range-aware sync would present stale pixels. The D3D11 backend
already has the shape to copy: sync_range_inner at nv2a_d3d11.c:1224 walks its
surface cache and syncs every surface overlapping the range.

5. THE INSTRUMENT SHIPS OFF, BECAUSE IT IS IMPLICATED IN A GUEST HALT
=============================================================================

RECOMP_SYNC_HIST, default OFF. Read the comment at sync_hist_on() in
nv2a_pb_exec.c before turning it on.

With the histogram accumulating unconditionally, a 240 s scripted run stopped
the guest dead at 9,480 flips. It is NOT a rendering freeze: flips,
guest_methods and 2D heard all froze in the same window and never moved again,
while the emulator's own threads kept running at 389% CPU. The control at HEAD
-- same schedule, same switches, same binary directory -- ran to 13,398 flips
with no repetition, and a player session on HEAD played ten minutes without it.

Every prior run in render-investigation/ prints its final flip count ONCE. The
instrumented run prints it EIGHT TIMES. That signature is new.

AND YET: that is one run per arm, which ab_score.py voids by policy and which
this project has already been burned by once. The code is a read of two
counters plus arithmetic -- no lock, no allocation, no Metal call -- so no
mechanism is apparent. A pre-existing intermittent hang, or timing
perturbation of one, fits the evidence as well; play_scripted.sh's own header
records that heavy probes destabilise this title.

SO IT IS UNRESOLVED, NOT EXONERATED, AND IT IS OFF. [FRAME] is deliberately
unconditional on the argument that an opt-in perf counter is one nobody has
switched on when they need it. That argument does not survive being implicated
in a halt. Two runs per arm before defaulting it on.
