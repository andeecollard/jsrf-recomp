1. FIXED AND PROVEN: THE CUTSCENE FREEZE
====================================================================

THE MORNING'S FIX COULD NOT HAVE WORKED. It took a recursive mutex at the top
of each of sub_0013B0A0 / sub_0013B0E0 and dropped it at the bottom. Read the
poisoning interleave again:

    A locks / B locks / A unlocks / B unlocks / A locks

Five complete calls, already in a serial order. A mutex held only INSIDE each
body permits that order unchanged. What the priority elevation prevented was B
ENTERING THE REGION WHILE A IS INSIDE IT -- a statement about the span between
A's lock and A's unlock, not about either body. The 430 s confirming run was
equally consistent with the interleave simply not occurring.

NOW: diagnostics/jsrf_first_fault/adx_guard.c. The guard is taken by the guest
lock and released by the MATCHING guest unlock, with the guest's own work in
between. Recursive (the guest nests, measured depth 3), owner-tracked (the spin
at sub_001437B0 issues unlocks it never matched with a lock), and bounded (a
lock never unlocked would otherwise wedge every other guest thread with no
diagnosis; after a timeout the waiter takes it and counts a steal).

    THE PROOF, from the player's session -- and it is the first time the
    mechanism has EVER been exercised:

        [ADX-GUARD] serialize on: locks=35525 unlocks=35525 matched
                    (+0 UNMATCHED) contended=43 max_depth=3 held=0
        [ADX] lock_count=0 saved_priority=1 raised=15 idle=-15

    contended=43 means 43 times a thread had to WAIT for another to leave the
    region. Every previous run in this project's history read contended=0 --
    the guard had never done anything. Those 43 are exactly the interleavings
    the per-body mutex would have let straight through.

    lock_count=0, not negative. saved_priority=1, not 15. Zero "lock_count is
    negative" lines. The old freeze signature is absent: the priority poll
    reads queries=27363, not the 32.6 MILLION of the frozen session.

THE PLAYER CLEARED THE CUTSCENE AND THEN THE WHOLE FIRST LEVEL.

jsrf_adx_guard_{off,zero,on} forces the five steps from a third thread with the
guest's two words and XAPI's 15<->16 mapping modelled exactly. The `off` arm is
the positive control and MUST poison. Run against the previous implementation
the `on` arm fails in under a second.

3. THREE BUGS FOUND BY TOOLS WE DO NOT ROUTINELY RUN
====================================================================

THE WINDOWS BUILD HAD NOT LINKED SINCE 4537424 (yesterday).
kernel_thread.c calls GetThreadPriorityXboxExact / SetThreadPriorityXboxExact
unconditionally at three sites. Both are DEFINED only in win32_compat.c and
DECLARED only inside that header's `#if !defined(_WIN32)` -- and on Windows
src/platform/CMakeLists.txt makes `platform` an INTERFACE library, so that file
is not compiled at all. Implicit declarations (mingw calls them errors), then
unresolved externals. They are not Win32 API; they are ours, added by the
priority commit. Windows now gets the same exact-value contract, keyed by
thread id. TWO CAVEATS: nothing retires an entry on thread exit, so a reused
tid inherits a stale priority (the POSIX side cannot have this -- its store
dies with the object); and it is UNTESTED AT RUNTIME, syntax-checked with
x86_64-w64-mingw32-gcc only.

THE D3D11 COMBINER READ CD AND AB SWAPPED. Two handovers recorded the
disagreement between d3d8_combiners.c and nv2a_texture_copy.c and neither
resolved it. Checked against xemu's parse_combiner_output: `out->cd = value &
0xF; out->ab = (value >> 4) & 0xF`. CD IS THE LOW NIBBLE. What it cost: JSRF's
graffiti shader emits 0x000820D0 = AB->R1, AB_DOT, AB_BLUE_TO_ALPHA. Read
inverted that is ab_dst = 0 = NV2A_REG_ZERO, which the emitter treats as
DISCARD -- so the tag's dot product was not written at all and the unused CD
product went to R1 instead. Fixed on the NV2A path in 777f04a; still broken on
Windows for this reason. It survived because it produced a MISSING WRITE, not a
wrong colour: a wrong picture gets reported, a missing write gets lived with.
The layout now lives in src/d3d/d3d8_combiner_bits.h and BOTH paths call it.

UNDEFINED BEHAVIOUR, 14 SITES. UBSan caught (0xFF << 24) at runtime; sweeping
for the shape found 13 signed-shift overflows (apu_regs.h x5, nv2a_regs.h x8,
all `1 << 31`). Plus a hand-rolled offsetof through a null pointer in
kernel_file.c -- in a file that already uses real offsetof 700 lines earlier.
After the fixes the whole suite is clean under -fsanitize=address,undefined:
0 findings over 111 passing tests.

  WATCH OUT: `ctest --output-on-failure` prints only FAILING tests' output, so
  a sanitizer finding inside a test that still PASSES is invisible. The first
  "zero findings" reading was an artefact of that flag. Re-run with -V it was
  62, all one benign class (UBSan's alignment check on the kernel-supplied
  ucontext_t in mcpx_trap_handler -- macOS's address, not ours; no sigaltstack
  here). Suppressed with no_sanitize("alignment") on that one function.

Also: nv2a_pb_test.c had a #ifndef fallback defining OP_TRIANGLES as 0x04 --
that is LINE_STRIP; the real value is 0x05. Dead only because nv2a_regs.h is
included four lines above it. Deleted.

5. THE TWO BLACK SCREENS ARE NOT ONE BUG
====================================================================

They are identical in every summary line in the log. They are told apart by the
PER-FLIP rate:

                          Roboy (t>=1086)     Load menu (t>=24)
    draws / flip                      1.0                  28.0
    triangles / flip                  1.0               2,129
    indices / flip                      3               6,387
    pushbuffer dwords / frame       1,098   (was 71,286)
    fixed-function                 FROZEN            CLIMBING (+29,800/report)

ROBOY IS NOT A RENDERER FAULT. The guest stops submitting a scene: one
3-vertex triangle per frame, forever. The [ITAIL] to 0x00075EB3 at t~1082 sits
exactly at the step where it collapses from 12.8 draws/flip to 1.0. (I earlier
called that ITAIL "downstream, not the cause" from 1-second [FB] sampling; the
draw-rate collapse orders it better and points back at it. Section 7.)

LOAD MENU IS THE RENDERER CASE, and it is a ~30 SECOND REPRODUCER: boot, main
menu, select Load. The geometry IS submitted -- 28 draws, 6,387 indices, 2,129
triangles per flip -- with EVERY refusal counter at zero ([TEXFMT] 0,
[COMBINER] 0, [VSH] rejected 0, metal hw refusals 0, batches dropped 0). It
renders exactly zero pixels.

RULED OUT, each with a measurement:
  - Save-slot thumbnails. SaveImage.xbx and TitleImage.xbx are NEVER READ (the
    [READ] line is unconditional per NtReadFile). Zero texture uploads in the
    entire black period -- 802 before, 802 after, every request a cache hit.
  - A fade-to-black multiply blend. [BLEND] src=0x306 dst=0x0 appears right as
    the screen darkens -- and appears at the SAME BOOT POSITION in the Roboy
    run, which then rendered for another 1,050 s. Not a discriminator.
  - Clear-after-draw, within the backend's binding: all 1,193 colour clears in
    the black period were refused for `target` and served by
    clear_unbound_slot, and surface_target only moves on a draw.
  - The filesystem. ZERO failed file operations in the whole run. Pressing Load
    opens Z:\Media\Disp\ (which exists: sprites, charicon, map) and U:\. The
    save reads back complete, 41,068 bytes, "JSRF" magic.
  - `want=280 got=52`, which appears 5 times in the failing run and ZERO in the
    good one -- a clean correlation and a dead end. It is SaveMeta.xbx, written
    by the TITLE (nothing in src/ writes it), containing
    `Name=JSRF Game Save Data` in UTF-16. The guest asks for a fixed 280-byte
    buffer and gets the 52 bytes that exist; bridge_write_iostatus passes the
    ACTUAL count with STATUS_SUCCESS, which is correct NT semantics. The
    correlation is just "a save exists".

WHY IT COULD NOT BE SETTLED FROM THE LOG. Three explanations remain --
geometry off-screen/zero-area, shaded black, or drawn to a surface we do not
present -- and on macOS EVERY number we have is read from GUEST RAM ([FB],
[FLIPTRACE], the presenter, the player's eyes). This backend deliberately
leaves guest RAM stale: clear_unbound_slot() clears the TEXTURE and sets
owes_guest_ram. So "the frame is in a Metal texture and the write-back lost it"
is INDISTINGUISHABLE from "nothing was drawn". nv2a_pb_exec.c already had the
right hook, with a comment saying so -- "what the GPU holds rather than what
guest RAM holds. Where they disagree is where the frame goes missing" -- and it
is #define'd on the WINDOWS branch only. That hole is now closed for Metal.

6. THE BOOST SOUND: A STALE IDLE HAND-OVER, NOT A CYCLE
====================================================================

Voice 15 went `on` at t=181.15 s and never received another off-command or
release-command; 894 s later it was still sounding. The guest kept issuing
off-commands for v1 (398 more starts), v14 (78), v3, v5, v12, v7, v18
throughout -- that is the positive control. Only v15 stopped.

MECHANISM: the guest's RemoveIdleVoice retired a voice our front end had
already RESTARTED 5.3 ms earlier. The ring entry's own flags say it:
`A` = the removed head still had PAR_STATE ACTIVE_VOICE set; `T` = cvl named
exactly v15, so the guest was servicing the idle trap for that voice. From that
instant DirectSound does not believe it owns v15, so no path will ever issue
VOICE_OFF. It is a LOOP voice (every voice this title starts is), so it never
ends by itself.

THE ENABLING DIVERGENCE IS MEASURED, and the existing instrument already said
it in words:

    guest methods dispatched while TRAPPED: 208001 (of 759378)
      -- each one overwrites the FEDECMETH/FEDECPARAM pair the guest has not
         read yet

On hardware a trapped front end has stopped decoding, so a VOICE_ON cannot be
processed while an idle-voice pair is outstanding. Ours decodes straight
through.

NOT A CYCLE, and NOT move-to-front -- see section 0. The relink count splits
mtf_head=499 (benign re-ON of the voice already at the head) + mtf_deep=207;
only the 207 can form one.

Changed, all in src/apu/apu_vp.c, all with =0 kill switches:
  RECOMP_APU_IDLE_HANDOFF_ACTIVE (default ON)  withhold the idle hand-over when
                                               the named voice is ACTIVE again
  RECOMP_APU_LIST_DEEP_UNLINK    (default ON)  prepending a node already in a
                                               singly linked list without
                                               taking it out writes a cycle
                                               into guest RAM; that is not a
                                               policy
  VOICE_ON self-link normalisation (unconditional)
RECOMP_APU_LIST_MOVE_TO_FRONT's default is DELIBERATELY UNCHANGED -- its
boot-anomaly gate is still open.

jsrf_apu_list_cycle_{default,mtf,off,bothoff} drives the real front-end
dispatch and asserts the SHAPE OF THE LIST READ BACK OUT OF GUEST RAM, not a
counter. Proven failing 4/3/2 assertions in three pre-fix configurations. The
off/bothoff arms REQUIRE the ring, so a repair that silently stops working
fails there instead of passing everywhere.

STILL A GENUINE CYCLE AT END OF RUN, and it is NOT the boost: [APU-IDLE-RING]
reads 3D 1 -> 3 -> 34 -> 1, built entirely from guest link writes the model

    [ITAIL] Unresolved tail jump to 0x00075EB3 (1 times)
    [ITAIL]   THE EPILOGUE NEVER RAN. esp is still inside the jumping

0x00075EB3 is arm 0 of the jump table at 0x00076610, whose only dispatcher is
sub_00075E90, inside CreateFullRoboyMenu. Three previous long runs had ZERO
[ITAIL] lines. This is the G20 stack-corruption class, live.

THE PLUMBING GAP: recover_midfunction_entries.py (already run by
regenerate.sh) builds a real body for "an address at an instruction boundary
inside an already-detected function" -- exactly this shape. But it only
operates on STUBS, i.e. addresses something statically CALLS. An arm reached
only through an unresolved indirect table never becomes a stub, so the recovery
pass never sees it. 445 arms are in that state.

AND A BODY IS NOT ENOUGH -- this is the part I had wrong in the brief:

    static const size_t g_recomp_table_size = 8875;   /* a LITERAL the lookup
                                                         loops over */
    sub_00075E90 in recomp_dispatch.c : 0 rows
    sub_00075E90 in recomp_stubs_unresolved.c : 1 body

Recovered stubs run because a caller has a static RECOMP_ABI_CALL to them. An
arm has NO call site; its only route in is RECOMP_ITAIL -> recomp_lookup ->
g_recomp_table. Every recovered arm needs a ROW and that size literal bumped.
(Latent bug found on the way: recover_icall_entries.py inserts rows and never
updates g_recomp_table_size, so its rows would be invisible. It is not run by
regenerate.sh, so nothing has paid for it yet.)

Built: switch_arm_entries.py joins the gate's existing arm walk to the recovery
pass; recover_midfunction_entries.py gained a second phase; regenerate.sh needs
no change. Dry run: 431 of 437 arms translate cleanly INCLUDING 0x00075EB3
(823 bytes, proper tail). The 6 refused are one cluster sharing a tail with an
untranslated `enter` -- a pre-existing lifter gap, correctly refused.

NOT PROVEN END TO END. It needs a REGENERATION to take effect and nobody has
run one. Measured effect on the gate: switch_unresolved +0, todo +0,
switch_arms_no_body 445 -> ~14, switch_resolved +49. Cost:
