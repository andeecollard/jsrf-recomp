=============================================================================

The DSOUND crash is not an occasional annoyance. It is destroying roughly half
of every measurement this project takes.

Eight crashed runs on 18 Sep, every one at sub_001A2E2E faulting on guest
0xFFFFFFBE. Between them they cost nodepth_ab its control arm (scored n=1 vs 3
and VOIDed), deferdepth_ab three control runs and the same VOID, forced

Nobody had been counting crashes per A/B, which is why this went unnoticed for
so long. Fixing it roughly doubles the value of every run. Until it is fixed,
budget six trials per arm and expect half to be excluded.

A rule came out of this and is in the goals: NO MORE A/Bs UNTIL THE CRASH IS
FIXED. That is arithmetic, not preference.

=============================================================================
THE CRASH, TRACED TO THE INSTRUCTION
=============================================================================

sub_001A2E2E+0x670, guest fault 0xFFFFFFBE. Every reported register is
reproduced by one path and no other:

    eax = MEM32(esi + 0x50);              ESI=0 -> page zero -> 0
    edi = ZX8(MEM8(eax + 0x18));          -> 0, matches EDI
    eax = eax + 0xFFFFFFB4u;              0-0x4C, matches EAX
    eax = ZX16(MEM16(eax + edi*2 + 0xA)); 0xFFFFFFBE -- THE FAULT

ESI==0 IS owner[h] being NULL. The chain is apu_vp.c:454. Page 0 is ordinary
mapped RAM (RECOMP_TRAP_NULL unset), so the NULL does not fault where it is
read -- it faults 0x4C bytes earlier and several loads later, which is why
this looked like an ESI bug for so long.

WHY IT IS ALWAYS VOICE 0, from the generated code and not inference: with
owner[h] NULL the two following loads read page zero, the compare tests the
handle against 0, and ANY h != 0 returns harmlessly. Only h==0 falls through
to the faulting call. That is why all 26 crash dumps name voice 0.

WHAT IS LEFT. The fatal handle is not one of our raises carrying a NULL owner
(item 7 above). So either it does not come from our raise at all -- the
decode-pair race, which RECOMP_APU_FEDEC_HOLD was built for and DEMONSTRABLY
DOES NOT FULLY CLOSE (it fired three times in one A/B with the hold on and
doing its job) -- or owner[h] is valid when we check and NULL by the time the
ISR reads it. Both are time-of-check/time-of-use. A raise-time check is in the
wrong place by construction. That is the next place to look.

PORTABILITY -- AND A BUG THAT AFFECTS EVERY NON-ARM64 HOST
=============================================================================

Prompted by a Steam Deck question. The Windows cross-build now compiles the
ENTIRE engine for x86-64 and reaches the linker with one unresolved symbol;
four test executables link as real PEs. Two shims did that, both matching
patterns already in the tree (sched_yield -> SwitchToThread, clock_gettime ->
QueryPerformanceCounter).

THE BUG: mcpx_hw_store, mcpx_hw_store_n and mcpx_hw_store_n_or_last are
defined ONLY inside `#if !defined(_WIN32) && defined(__aarch64__)`, while
xbox_memory_layout.c calls two of them from unguarded code at :598 and :1249.
A native x86-64 Linux build fails identically. It has been invisible because
nothing but macOS ARM64 has been linked since it landed.

NOT FIXED ON PURPOSE. g_mcpx_alias and MCPX_WBASE are already outside the
guard so it looks tractable, but line 326 explains the double mapping replaced
the mprotect window discipline -- and that discipline is the fix for the
incident CLAUDE.md records as 13.5M open windows in 45 s swallowing every
VOICE_ON. Windows traps MMIO differently. This needs a decision from someone
who owns that path.

We do NOT use D3DMetal or DXVK and should not on macOS: nv2a_metal.m links
Metal.framework directly, and every improvement shipped today lives in it.
Translation layers are for hosts where there is no backend -- Linux and Deck.
