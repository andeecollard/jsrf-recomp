1. THE HEADLINE FOR THE REVIEWED
=================================
The handover asked me to satisfy myself that a gate passing on a broken
renderer is the finding rather than the tool. It is both, and worse than
stated: metal_batch_test has never performed a depth COMPARISON, on either
path, in any phase.

Two fixture defects, each hiding the other:

  * Every phase sets `s.depth_func = 4`. That is a D3D-style D3DCMP_LESSEQUAL;
    the NV2A encodes compare functions in the 0x200 range, so
    nv2a_metal_compare_func returns -1 and BOTH paths fall back to ALWAYS. The
    code comment at nv2a_metal.m:982 says this outright. Nobody connected it
    to the gate that reads the test's output.

  * base_state() builds the state with memset(0), leaving
    z_clip_min == z_clip_max == 0. The software path clamps every fragment
    into that range when z_cull is off, so ALL of its depth was zero.
    nv2a_texture_copy.c:76 normalises that pair back to [0, 16777215] when it
    decodes the guest registers, so no real draw can reach the backend with
    it. Only a fixture filling the struct by hand could.

With no depth to compare and no comparison to make, the depth half of the gate
measured nothing. The proof is a negative control: injecting
`d.depthCompareFunction = MTLCompareFunctionAlways` into hw_depth_state_for --
breaking depth testing outright on the hardware path -- produced a PASS with
numbers identical to the last digit.

WHICH MEANS THE ACCURACY CLAIM WAS THE ARTIFACT. metal_hw_check.sh's own
comment reads:

    software state    1 of 65536 pixels,  54091 of 262144 depth bytes differ
    hardware state    1 of 65536 pixels,     25 of 262144 depth bytes differ

and concludes the hardware path "is the BETTER approximation" because it "takes
z from the rasteriser's own depth interpolation, which is what the NV2A does".
The 54091 is the software path being fed a depth range it clamps everything
into. Give the fixture a legal range and the same two arms read:

    software state    24 of 262144 depth bytes differ
    hardware state    25 of 262144 depth bytes differ

deterministic over three runs each. The gap is one byte, the other way. The
hardware path may still be the better approximation for the reason given, but
this measurement has never shown it and the sentence should not survive.


2. WHAT THE GATE ACTUALLY MISSED, WHICH IS NOT WHAT SECTION 5 GUESSED
=====================================================================
Section 1 of the handover said "NOTHING SCORED A FRAME FROM A REAL RUN". True,
and there is a smaller, cheaper statement inside it: nothing scored a surface
swap either, and the reason is not the one recorded.

The handover says "the synthetic test changes surface once". It does not.
metal_batch_test phase D alternates two render targets forty times, on purpose,
with a comment explaining why. What is missing is the SCORE: the only oracle
comparison in the program is phase A, and phase A never changes surface. D is
compared batched-against-per-draw, which is orthogonal to whether either is
right. metal_hw_check.sh reads phase A's numbers, so the swap was invisible to
it.

Second hole, not noticed anywhere: metal_hw_check.sh never set
RECOMP_METAL_565. The configuration reported broken is HW=1 AND 565=1 -- a
different attachment format, a different upload path and a different readback
path -- and the gate scored neither arm of it.

Both are now closed. Phase F draws 120 triangles across THREE alternating
surfaces (the count the title holds) with a real guest LEQUAL, scored against
the rasteriser; metal_hw_check.sh scores phase A and phase F across three arms.

Read it as follows.

  * THE THREE-SURFACE SWAP DOES NOT REPRODUCE IT. Every arm scores the same 29

  * 565's EXTRA PIXELS CONFORM. 697 and 1513 pixels differ, and every one of

  * THE 29 PIXELS ARE NOT A SWAP DEFECT. They are scattered singletons across
    all three surfaces (10/14/22), present with blending off, present with
    depth testing off, and present with ONE surface. They scale with the number
    of triangle edges drawn, which is what a rasteriser coverage disagreement
    does.

So the wrong image at a real mission is still unexplained, and the surface
swap is now evidence against rather than a lead. What this gate STILL does not
exercise, and a real mission does: register combiners, alpha test, stencil,
multi-texture. That is where I would look next.


4. SECTION 5 ITEM 1's SECOND SUSPECT IS VOID -- DO NOT SPEND A BOOT ON IT
=========================================================================
"setDepthClipMode:MTLDepthClipModeClamp at the draw site ... added
speculatively ... Revert it first and re-test."

It cannot be the difference, and reverting it cannot change anything, because
the clamp is already applied to BOTH paths. nv2a_metal.m:2064 sets it
unconditionally on the encoder, before the `if(hw)` branch, and has since the
13 Sep depth-clipping retraction -- with a paragraph explaining that the
fragment shader now owns the guest's SET_CLIP_MIN/MAX policy and hardware
clipping would pre-empt it. The call inside the hw branch is a SECOND call, on
the same encoder object, setting the same value. It is dead code.

Removing the hw-path call: no behavioural change. Removing the unconditional
one: changes both paths equally, so it still cannot explain a difference
between them.


5. A REAL CRASH, FOUND AND FIXED
=================================
    RECOMP_METAL_HW=1 RECOMP_METAL_BATCH=1 jsrf_metal_batch_test   ->  SIGSEGV

nv2a_metal_draw bound `encoder` to the open batch encoder, then -- eighty lines
later, after already issuing setDepthClipMode on it -- called batch_flush() to
honour "a batch encoder is opened from ONE pass descriptor". batch_flush() ends
the encoder, commits its command buffer and nils batch_encoder. The local
`encoder` still pointed at it, so every setRenderPipelineState, setVertexBuffer
and drawPrimitives below went to an encoder that was already ended.

It fires on the FIRST hardware draw of any process, every time:
batch_encoder_hw is a static initialised to 0, hw is 1, so the very first
hardware draw always takes the flush branch.

Nothing saw it because no gate combines the two switches. metal_batch_check.sh
runs RECOMP_METAL_BATCH with the hardware path off; metal_hw_check.sh runs
RECOMP_METAL_HW with batching off.

Fixed by moving the check above the encoder acquisition, where the comment
always said it belonged ("batch_flush() BEFORE switching"). After the fix the
batched hardware path runs clean and its dump is byte-identical to the per-draw
hardware path.

26 are traces, audits, reports and dumps, where presence is the correct test

    RECOMP_PAD_INJECT           main.c:1857

RECOMP_PB_EXEC is the one that matters. It is the master switch for the whole
NV2A executor, it appears as `RECOMP_PB_EXEC=1` in CLAUDE.md's own run line,
and `RECOMP_PB_EXEC=0` would leave it ON -- a control arm that is not a
control, on the most load-bearing switch in the project.

RECOMP_OHCI_MIE is the sharpest trap: the comment beside it literally reads
"RECOMP_OHCI_MIE=1 also sets MasterInterruptEnable", and =0 sets it too.

Nothing in the tree currently passes =0 to any of the eleven, so no live
measurement is wrong because of this. Converting them to `atoi(e) != 0` is
mechanical; RECOMP_LEGACY_ZCLAMP is the urgent one because it is a documented
A/B arm ("RECOMP_LEGACY_ZCLAMP=1 forces the old saturate-instead-of-discard
policy, to A/B the change in one binary") that cannot be A/B'd.

=========================================
Items 2, 3 and 5 below are now done and committed. Their results change the

THE STATE COVERAGE ALREADY EXISTED, IN A TEST NOTHING RAN. Before writing a
phase G for combiners, alpha test and stencil, it was worth checking what was
already there: metal_copy_test compares the backend against the rasteriser with

It is built on Apple and registered with nothing -- out of ctest because it

state coverage in the tree had never been executed, which is the same shape as
the phase-A-only problem in section 2.

Run across the three arms:

    software state    FAILS at line 49 -- the depth readback after a
                      depth-tested draw, known and tracked
    hardware state    exact match
    hardware + 565    exact match

That is the strongest result of this review. Combiners, alpha test, stencil and
multi-texture are BYTE-EXACT on the hardware path, and the software path is the
one that misses. It is also the evidence the retracted 54091 was standing in
for, and a stronger claim than that ever was, because it is exact equality
rather than a tolerance.

And it narrows the remaining space sharply. Every per-draw state translation a
mission uses is now known correct in isolation on the hardware path. The wrong
image is therefore NOT a mistranslated combiner, blend factor, stencil op or
compare function. What is left is behaviour over time or at scale: the retained
surface across frames, the clear/flip interaction, the presenter round trip --
none of which any device test reaches, because they all begin from
nv2a_metal_invalidate and run a few dozen draws.

THE SWITCH SWEEP HAD TO BE WIDER THAN THE PATTERN. RECOMP_PB_EXEC is read in
four places in three spellings; the `? 1 : 0` form the handover named finds one
of them. Ten behavioural switches now go through recomp_switch_on(), which
treats "0" and empty as off and everything else as on -- the conservative
conversion, so nothing that turns a switch on today changes. RECOMP_FAKE_PAD
stays on presence and is annotated to say why: its value is meaningful (1, <n>,
`a`, `always`) and an atoi() conversion would silently disable `=a`.

I also nearly filed a fourth instance that was not one. RECOMP_OHCI_ATTACH
looked presence-tested to the pattern match, and oracle_anchor.sh's
ORACLE_NO_OHCI_ATTACH writes RECOMP_OHCI_ATTACH=0 -- which looked like a live
broken control arm. Reading the predicate rather than the grep shows it already
excludes "0" and the empty string, and main.c's two `!getenv` sites are a
default-setter, not a gate. The rule that catches counters catches greps too.


10. THE CAUSE OF THE FLICKERING CHECKERBOARD
=============================================
FOUND, AND IT IS NOT A FRAME-BOUNDARY PROBLEM AT ALL. It is one draw, and the
gate could have caught it on day one if the fixture had set one field.

base_state() builds its state with memset(0), so s.dither was 0 in every phase
of the only test that scores an image. The one code path in this renderer that
produces a literal 4x4 lattice had never been executed. That is the THIRD
fixture field found this way, after depth_func = 4 and the zeroed clip range,
and it is the one that mattered.

Set it and the paths separate at once:

                        pixels differ   beyond one step   4x4 dither cells
    software state            0                0            0 / 0
    hardware state         8192               19           77 / 857
    hardware + 565         8402               19           93 / 878

The software path becomes EXACT -- 0 of 65536, worst error 0 steps, better than
the 1 pixel it scored with dither off. Dither is not noise; it is something the
oracle does and the gate was not asking about.

THE MECHANISM. The two fragment shaders apply the dither at different stages:

    fs      shade -> blend (in shader) -> dither -> store
    fs_hw   shade -> dither -> return  -> [blend unit] -> store

The NV2A dithers at the ROP, after blending. fs does that, and so does
nv2a_texture_copy.c at its store. fs_hw hands the biased colour to the
fixed-function blend unit instead, so the +/-0.5 LSB nudge is multiplied by the
source blend factor and mixed with a destination that already carries its own
baked-in bias, instead of being applied once at quantisation.

MEASURED, NOT INFERRED, and this is the part that makes it certain:

    dither ON, blending OFF     hardware scores 0 of 65536 -- exact
    dither ON, blending ON      hardware scores 8192

The error exists only where both are active. That is the ordering and nothing
else.

AND IT IS A PATTERN, NOT MORE NOISE. The emptiest and fullest of the sixteen
4x4 dither cells hold 77 and 857 differing pixels. Coverage disagreement -- the
kind every other phase carries -- fills all sixteen evenly. An order of
magnitude apart is the dither matrix's own shape, and the test now reports that
cell range so the distinction needs no image.

That is the flickering checkerboard: a 4x4 lattice error that compounds with
each overlapping blended layer, over backgrounds that are mostly overlapping
blended layers, changing frame to frame as the camera changes how many overlap.

NOT A ONE-LINE FIX. Metal has no ROP-stage dither and the blend unit runs after
the fragment shader, so this path cannot dither where the hardware does.
Skipping the shader dither when blending was measured and is WORSE -- 92 pixels
beyond one step against the current 19 -- because the oracle dithers and the
hardware path then would not. The real options are a third pipeline that blends
in-shader while keeping the real depth and stencil attachments (losing the
ordering win only for dithered blended draws), or a documented divergence. That
is a design decision.

NOT MEASURED: the magnitude at scale. This is 20 blended draws; a mission has
far more overlap and compounding is the whole mechanism. The structure is
confirmed; its size in a real frame is not.

metal_hw_check.sh NOW FAILS, deliberately, naming this. Leaving dither out to
keep it green would be the exact failure this review has been about.


11. THE FRAME-BOUNDARY TRACE, AND WHAT IT FOUND
================================================
Done before the above, and it is how the search got narrow enough to look at a
single draw again. What survives a frame, all of it in nv2a_metal.m and all for
exactly ONE surface:

    surface, stencil_surface, hw_depth_tex, hw_stencil_tex   reallocated per swap
    surface_target / depth_target + geometry + valid/dirty
    hw_pso[16] / hw_dss[16]      keyed caches, never invalidated
    texture_cache[128]           keyed by address AND a full memcmp
    ring slabs, last_command, batch_*

Reset points: the upload block (any pointer or geometry change),
nv2a_metal_sync (readback), nv2a_metal_invalidate(target) (per surface), and
nv2a_metal_discard (which took no target at all -- fixed, see below).

CONFIRMED AND FIXED. nv2a_metal_discard dropped the retained surface without
reading it back and without being told which surface the guest was clearing.
s_gpu.color_offset moves on the register write, surface_target on the next
draw, so a clear in that window names one surface and drops another. Measured
at 24848 of 65536 pixels of finished rendering lost. Latent -- default off, and
the reproducing run reports "clear discards=0" -- so nothing recorded is
affected.

CONFIRMED, NOT FIXED. nv2a_gpu_sync_range(target, bytes) is
#define'd to nv2a_metal_sync() and discards its target. Benign while one
surface is retained; wrong the moment that changes. And hw_565_on() never
consults hw_depth_tex, so a depth-texture allocation failure would leave a
B5G6R5 attachment bound while draws fall to a pipeline built for RGBA32Float --
corruption instead of a clean fallback. Not reachable in any observed run.

UNVERIFIED. The presenter reads s_snap while snapshot_surface() writes it, and
snapshot_surface() can realloc it. dev_Present runs on the render thread; I
could not establish whether the pushbuffer executor is the same thread without
a run.

ELIMINATED WITH EVIDENCE, all of which I had first proposed as causes:
  * clip-origin mismatch -- clip is +0+0 in all 1275 reports of every archived
    mission run
  * texture cache staleness -- a hit requires a full memcmp of the contents
  * pipeline/depth-state cache overflow -- pipelines=4..5, refusals=0, cache 16
  * the batches-vs-hw-draws gap of 7381 -- empty batches returning early, and
    the same 0.6-1.1% rate in all three arms
  * an unordered tile-memory race from dropping raster_order_group(0) --
    fs_hw returns float4 and takes no destination read, so there is nothing to
    race on

ON PROCESS. Four of the six hypotheses in this section died, two of them after
I had written them up as findings rather than as guesses. Nothing false reached
a commit, because each was checked -- but in a project whose recorded failure
mode is believing a number before reading what produced it, generating the
narration ahead of the evidence is the wrong order, and I did it while
reviewing a handover about exactly that. The dither result above is what the
right order looks like: predict, measure with a control (blending off), check
the shape (the lattice), then write it down.
