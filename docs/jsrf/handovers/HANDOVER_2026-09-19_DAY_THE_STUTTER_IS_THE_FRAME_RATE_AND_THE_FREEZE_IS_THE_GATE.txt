1. THE INTRO STUTTER: DIAGNOSED, NOT FIXED, AND NOT AN AUDIO BUG
=============================================================================

Reported by the player six times today as "intro sound still stuttering" /
"the sound is hanging from the intro into the game". Every rival cause is
measured at zero with a live positive control beside it:

  [APU-BIN]    2D lost=0  3D lost=0            heard 67,450 / 2,718
  [APU-PACE]   starved=0  empty=0              min_queued 26.7 ms, 48,000 Hz
  [APU-IEN]    0 suppressed                    42 raises allowed
  [APU-SGE]    0 implausible                   8.4M + 4.1M translations
  [APU-ADPCM]  fail=0 silenced=0 (fixed today) 1,469 blocks recovered

The mechanism, from the APU agent, with the arithmetic:

  The CRI sound server (sub_0013B1C0) blocks in exactly one place, a
  reset-then-wait with Timeout=NULL on one object via KeWaitForSingleObject
  (thunk 46 -> ordinal 159). It moves AT MOST 1024 samples per pass (clamp
  at guest 0x0013E965), so 44.1 kHz needs >= 43.1 passes/s. Its pass rate
  tracks the FRAME RATE: bridge_KeWaitForSingleObject is a spin-poll that
  pumps vblank/device/timer delivery on the blocked thread itself, so the
  server delivers the very interrupt that wakes it.

  Below ~43 fps the producer falls short and the voice ring replays for the
  deficit. The shortfall equals the replay fraction EXACTLY, three times:

    32,513 written / 44,123 consumed  = 26.3% short  = 26.3% stale  (25.5 fps)
    35,471 / 44,079                   = 19.5%        = 19.5%        (21.1 fps)
    44,117 / 44,117                   =  0.0%        =  0.0%        (49.8 fps)

  At >= ~49 fps the guest writes precisely 44,100 samples/s = 43.07 x 1024,
  the clamp, saturated.

  Pre-registered and confirmed: RECOMP_IRQ_THREAD (which now runs -- see
  section 6) changed nothing, because nothing on the APU interrupt path
  signals the server's event. The title imports only KeSetEvent and
  NtSetEvent, ten call sites, and the APU's own DPC (0x001A26C1 ->
  0x001A2497) signals none of them. Vblanks were delivered at 57.8 Hz
  throughout while the server got 25-34 passes/s.

What was NOT established:
  - That the player's 21-25 fps is a SUSTAINED rate. The render agent
    measured 39-44 fps mean at mission entry with a p90-p99 tail at 21-25
    ms and 129 of 391 frames over 33 ms. So the criterion is the TAIL, not
    the mean, and the stutter is intermittent -- which matches the report.
  - That the server's object is the same event the vblank DPC sets. The
    agent proved the negative (nothing on the APU path signals) and walked
    the DPC two levels, not to closure.

So: get the intro's frame-time TAIL under 23.2 ms and the stutter goes.
Speed is the same problem -- the game is frame-locked.

Two things the "stutter" is NOT, both refuted with positive controls:
  - The staging ring recycling under an in-flight draw: 4,681 wraps, 0
    waits in the shipping config; squeezed to 2 x 256 KiB the same counter
    reads 49,871, so the instrument fires; an unpinned arm with ~56,000
    unprotected reuses rendered correctly.
  - The 99.8%-stale "voice B": it is voice 69, a static looping effect at
    0.84 laps; stale is what looping MEANS for a non-streamed buffer. The
    counter now withholds its verdict below two laps (1c47e9f).

2. WHERE THE FRAME GOES, AND WHAT I GOT WRONG ABOUT IT
=============================================================================

Measured by the render agent with per-caller nanosecond attribution that did
not exist before (2fb4f6d), completed runs, player's own 35-switch set:

  sync cost by caller: external 4835 calls, 22974 ms waiting, 1608 ms reading back
  sync cost by caller: swap     9624 calls,  2425 ms waiting, 1566 ms reading back

Against 59.7 s of frame time: the FLIP's wait is 38.5% of everything, the
swap's is 4.1%. `rest` (the wall-clock residual = the recompiled guest) is
flat at 3.3 +/- 0.1 ms while the frame swings 16 -> 26 ms. The slow frames
are made of `sync`, i.e. the CPU blocked in [last_command
waitUntilCompleted] waiting for the GPU.

Three leads I gave that agent, and their fate:
  - "7,493 clears, each a drain and a 4.9 MB read-back" -- FALSE. The log
    line ends "...that did not happen" and I quoted it truncated at 150
    characters. clear_encode is an empty render pass with
    MTLLoadActionClear, no wait; [STAGE] clear is 0.07-0.09 ms per frame.
  - "5,335 surface swaps forcing a sync" -- TRUE but 4% of the bill. Gone
    now; worth 2-3% on scene-matched windows. The general fix is right: a
    sync's wait exists only to make a read-back valid, so a sync with
    nothing to read back must not take it. RECOMP_METAL_DEFER_SWAP was
    inert because depth_dirty stayed set after surface_dirty cleared.
  - "rest = 15.49 ms is the largest single item" -- FALSE, vsh+submit
    exceeded it in the very line I quoted, and it is not the variable part.

Two real bugs found on the way, both fixed and counted:
  - The LRU pick inside a surface rebuild is not surface_cache_drop and
    never paid owes_guest_ram: it overwrote the only copy of an unbound
    surface. One eviction a run today.
  - Render-to-texture uploads straight from guest RAM while
    clear_unbound_slot leaves 7,164 deferred debts a run with defer_swap
    OFF: 8 texture uploads per run were reading PRE-CLEAR contents in the
    shipping configuration.

And one gate: jsrf_ff_msl_diff_test was FAILING in the shipping switch set
and passing only with RECOMP_FF_TEXMAT_IDENTITY=1, which the player does
not set. RECOMP_METAL_FF=1 was enabled BECAUSE that test passed. The agent
found the TEST was wrong (nv2a_ff_key is right to refuse an all-zero
enabled texture matrix) and fixed the test, not the default (158ca90). Do
not flip the switch to make it green.

RECOMP_METAL_DEFER_SWAP: do not turn on yet. Hazards closed, but n=1 per
arm and it changes when guest RAM becomes correct. Wants a second pair.

3. THE SKATING CRASH: CHARACTERISED, DETERMINISTIC, NOT FIXED
=============================================================================

Four times today, same walker, same call chain, same nodes, same offsets:

  EXC_BAD_ACCESS at guest 0xFFEEFFF2 (first crash: 0xFF555559)
  sub_00011D00 x10-13 recursive
    <- sub_000123E0 <- sub_00013A80 <- sub_00013F80 <- sub_0006F9E0
    <- sub_00147FB4 <- kernel_thunk_dispatch <- sub_00147F53 (main thread)
  ECX=EDI=FFEEFFEE  EBX=00FFFFFF (first crash) / FFEEFFEE  ESI=80000000
  EDX=3F800000  572-644 bytes of guest stack used

sub_00011D00 is a scene-graph walker: [edi+0x28] child, [edi+0x30]
sibling, recursing on the child, iterating siblings. It faulted on
MEM32(edi+4). Its prologue saves the caller's `this` on the guest stack
(push ecx; push ebp; mov ebp,ecx) so the parent survives the fault.

Established, all measured:
  - OUR TRANSLATION IS BYTE-EXACT. All 157 bytes of the guest function
    disassembled and compared instruction by instruction against the
    generated C. The recompiler is not at fault. The merge is cleared too:
    every function on that stack is byte-identical across upstream v0.10.0
    except the outermost, which gained `ebp = g_ebp` at a thread entry
    where g_ebp is thread-local and zero.
  - 0xFFEEFFEE IS THE GAME'S OWN SENTINEL, not corruption and not ours. It
    sits in guest RAM as 224 isolated words in 155 runs, longest run 2 (a
    colour buffer would be thousands in a row -- that hypothesis is dead).
    Our tree writes it nowhere. It appears once in the guest image, at
    .text 0x00148F34: `mov dword ptr [esi+0x10], 0xffeeffee` inside
    sub_00148E69 (0x00148E69..0x00148F87), allocator bookkeeping surrounded
    by page-shift arithmetic. 0xFF555555 from the first crash appears 24
    times in the image -- also guest data.
  - The guest's own recursion guard is `test ecx, ecx` -- a ZERO check. A
    sentinel passes it. On hardware [edi+0x28] is presumably zero or a
    node; in our run it holds an allocator marker.
  - The wild-pointer instrument (section 5) found four objects holding the
    value and NONE of them was the field the walker read. Two of them --
    040FFF40 -> 040FFFA0 (the CActSequence object) -- have real .rdata
    vtables. The region it descended into, 0x04000500-0x04000640, is a run
    of self-linked LIST_ENTRY pairs (InitializeListHead output) whose
    "vtable" points at itself. The walk marched 0x28 bytes at a time through
    a list-head array until it hit the sentinel.

What is NOT established, and the retraction:
  - WHICH real node handed the walk a list-head array as a child. I
    reconstructed a chain from the dumped stack (04838934 -> 04000508 ->
    040004D8 -> 04000500 -> 04000528) and reported it. It is UNSOUND: at
    0x00011D1E the function does `mov [esp+0x10], ebx`, reusing the saved-
    ecx slot as an ebx spill, so the slot I read as "`this` passed in"
    holds ebx for every frame past that point. The saved edi at +8 IS
    sound (never spilled), and the descent decoder in main.c (98be4bb)
    now reads that and prints MEM32(edi+0x28) beside it -- but it has not
    fired on a real crash yet. Item 0.3 is the sure route.
  - The scripted pad cannot reach this crash. It dies first at the
    DirectSound ISR (section 4) or parks at the title.

4. THE DIRECTSOUND ISR CRASH: MEASURED AND GUARDED
=============================================================================

sub_001A2E2E +0x6A4, 26 prior dumps all naming voice 0, and the one that
gated every scripted run at the title screen.

The post-mortem instrument printed what the old report dropped:
  IMPLIED GUEST VA: 0xFFFFFFBE     FAULT CARRIED BY: EAX(FFFFFFB4)+0xA
0xFFFFFFB4 = 0 - 0x4C: a CONTAINING_RECORD on NULL, confirmed in the
disassembly (001A2E8F `add eax, -0x4c`; 001A2E95 faults).

I first said the NULL was [esi+0x50]. WRONG: esi ITSELF is NULL -- ECX reads
exactly 0x6C4 = MEM32(esi+8) + h*8 + 0x6C4, which needs both terms zero,
and ESI=00000000 is printed outright. Page 0 is mapped RAM here, so +8,
+0x50 and +0x18 all read zero without faulting, and [esi+0x50] was just
the last zero to reach a register. Same in every archived dump.

The mechanism (APU agent, 13294ff): a TOCTOU. The guest's teardown
(sub_001A1E01) raises an interlock at this->0x2C0, strikes out the handle,
clears owner[h], drops the interlock; the frame above the unguarded read
begins "if (this->0x2C0 != 0) return". That is why the ISR may skip a NULL
test on hardware. Ours fails both halves: the raise comes from OUR list and
pci_irq_assert is a no-op so delivery is up to 8 ms late, after the
interlock is released. So the check belongs at the HAND-OVER (001A25AA's
read of FEDECMETH), not at the raise.

Six 240 s runs scored on FAULT SITE, not "did it crash" (two died elsewhere
entirely, one never left the attract loop):
  guard OFF, owner[0] cleared at the hand-over -> died at sub_001A2E2E+0x6A4
  guard ON,  same combination x3             -> all withheld, played to 30
RECOMP_APU_IDLE_HANDOFF_GUARD=1 is in the player's config. The player's
run with it: reads=6 owned=6 NULL=0 h0=0 withheld=0, no crash.

Also: "[APU-IDLE-OWNER] NOT MEASURED" is gone for good. The DirectSound
object was in the kernel's interrupt table all along as vector 5's
ServiceContext (43068ed), confirmed against the exact byte-matched symbol
?HandleFETrap@CMcpxAPU@@IAEXXZ, a thiscall with no parameters. And
owner[]'s free marker IS the literal zero (three writers in the image), so
the sentinel concern from section 3 does not apply to this array.

Still wanted: three guard-off top-up trials to finish the A/B. n=1 per arm
today because I kept taking the run slot off the agent.
