1. THE METHOD, WHICH FOUND EVERYTHING
=====================================
Every bug this session had ONE SHAPE: an x86 behaviour emitted as the nearest C
construct where C differs at a single edge, or emitted as nothing at all.
Ordinary inputs pass either way, so tests and casual play never see it.

And ONE TELL: **split every population by REACHABILITY before reading its
count.** Raw counts here are dominated by functions nothing calls -- data swept
as code -- and the raw number sends you to the wrong component:

    dead branches        104 -> 90 total  BUT  18 -> 4 reachable
    unimplemented insns  176 -> 164 total BUT  12 -> 3 reachable

Both totals barely moved. Both reachable counts fell by about 78%. A change
that looks like noise in the total is the whole of the work.

4. THE OPEN RENDERING BUG, AND A DIAGNOSTIC THAT IS NOT THE FIX
===============================================================
Reported: background geometry vanishes in WHOLE FLAT CHUNKS as the camera
moves. Characters are fine.

Measured clean, so these are excluded: 70M triangles rasterised, 0 batches
skipped as not screen-space, 0 triangles off-surface, 0 Metal software
fallbacks, 0 texture rejects. Geometry reaches the rasteriser.

The Metal path is a SOFTWARE rasteriser: it takes already-transformed
screen-space vertices and does its own depth test in the fragment shader
against a 24-bit Z packed into the surface's ALPHA channel. There is no depth
attachment. But Metal still clips to 0 <= z <= w by default, so any triangle
whose z leaves [0,1] is discarded before the shader can judge it.

`RECOMP_METAL_DEPTH_CLAMP=1` turns that clipping off. A/B in ONE binary:

    clamp off:  11980 polls, 15.26M triangles
    clamp on:    6085 polls, 18.46M triangles

So geometry IS being z-clipped -- 20% more of it survives -- but clamping
HALVES the frame rate, because geometry past the far plane is squashed onto it
and rasterised over large areas. It is therefore a diagnostic, left OPT-IN and
OFF by default. Do not ship it.

THE REAL QUESTION: why does z leave [0,1] for geometry the title expects to be
visible? That is upstream, in whatever produces the screen-space z in
nv2a_pb_exec.c. Start there, not in the Metal file.

Also unexplained and possibly related: `[VSH] rejected=59  oPos is not finite`.
59 batches with NaN vertex positions. The count is STATIC across reports, so it
happens early and stops -- not the ongoing clipping, but NaN reaching geometry
is exactly what cost two days this morning.
